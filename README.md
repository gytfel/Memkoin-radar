# Memecoin Wallet Radar

Анализ кошельков Solana по on-chain данным + телеграм-радар, который присылает
сигнал, когда несколько проверенных кошельков одновременно заходят в один токен.

---

## Сначала важное: про 80–85%

Ты просил, чтобы каждая сделка была в плюсе с вероятностью 80%. Такого не
существует ни у одного трейдера, фонда или бота — на мемкоинах тем более.
Кто это обещает, продаёт подписку, а не сигналы.

**Но 80% winrate тебе и не нужен.** Считай:

| Стратегия | Winrate | Стоп | Тейк | Мат. ожидание на сделку |
|---|---|---|---|---|
| «нужен 80%» | 80% | −25% | +40% | 0.8·40 − 0.2·25 = **+27%** |
| реалистичная | 40% | −25% | +100% | 0.4·100 − 0.6·25 = **+25%** |
| реалистичная | 35% | −20% | +150% | 0.35·150 − 0.65·20 = **+39%** |

Третья строка **лучше** первой, хотя проигрывает 2 сделки из 3. Прибыль делает
не частота попаданий, а асимметрия: маленький фиксированный убыток против
большой открытой прибыли. Поэтому в конфиге целься в `expectancy`, а не в winrate.

И ещё: кошелёк с winrate 90% может быть убыточным. Запусти `python selftest.py` —
там четыре реальных паттерна, включая кошелёк с 80% плюсовых сделок и минусом
по деньгам. Анализатор такие отсекает.

### Почему на трекерах полно кошельков с «90% winrate»

1. **Спрятанные мешки.** Считают только закрытые сделки. Раги остаются висеть
   в кошельке и в статистику не попадают. Здесь считаются две цифры:
   `winrate` и `winrate (мешки=0)` — вторая честная.
2. **Фарм микро-суммами.** 300 сделок по 0.02 SOL с профитом +5%. Флаг `farm_like_size`.
3. **Снайпер-боты.** Держат позицию 20 секунд. Руками ты за ними не успеешь
   физически. Флаг `sniper_bot`.
4. **Survivorship bias.** Кошелёк угадал 3 токена и попал в топ трекера, а 200
   таких же слились и их никто не видит. Отсюда `min_closed_trades: 30`.

Поэтому в конфиге стоит `max_win_rate: 0.85` — кошельки **выше** 85% отклоняются
как подозрительные. Ровно та цифра, которую ты искал, работает как красный флаг.

## Как реализовано «не присылать, если winrate ниже 80%»

Заранее вероятность неизвестна, поэтому она **замеряется**:

1. Каждый сигнал пишется в `signals.db` вместе с условиями входа
   (сколько кошельков зашло, ликвидность, возраст токена) → «бакет».
2. Бот сам ведёт сделку до тейка или стопа и записывает исход.
3. `signal_journal.gate()` смотрит фактический winrate по этому бакету.
4. `gate_mode: hard` → пока замеренный winrate ниже `target_hit_rate`,
   сигналы из этого бакета **не приходят вообще**. Ровно как ты просил.
5. `gate_mode: shadow` → приходят с пометкой, чтобы ты видел, что теряешь.

Честное предупреждение: с `target_hit_rate: 0.80` и `gate_mode: hard` бот, скорее
всего, замолчит навсегда — потому что ни один бакет столько не даёт. Это не баг,
это и есть ответ на вопрос «бывает ли 80%». Начни с `0.45` и тейком `+100%`,
через месяц посмотри `/stats` и решай по реальным цифрам.

## Файлы

| Файл | Что делает |
|---|---|
| `wallet_analyzer.py` | тянет свопы, восстанавливает сделки по FIFO, считает winrate / expectancy / profit factor, ставит красные флаги, отбирает годные кошельки |
| `discover.py` | ищет ранних покупателей уже отработавших токенов → список кандидатов |
| `token_safety.py` | ликвидность, FDV, mint/freeze authority, топ-10 холдеров, rugcheck |
| `signal_journal.py` | sqlite-журнал сигналов + замеренный winrate + гейт |
| `radar_bot.py` | телеграм-бот: конфлюэнс покупок → проверки → сигнал → ведение до TP/SL |
| `selftest.py` | проверка всей логики на синтетике, без API-ключей |
| `config.yaml` | все пороги |

## Установка

```bash
pip install -r requirements.txt
cp .env.example .env      # вписать ключи
set -a && source .env && set +a
```

Нужен один ключ: [helius.dev](https://helius.dev) (бесплатный тариф хватает для
старта). Dexscreener и rugcheck работают без ключа.

Токен бота — у `@BotFather`, `chat_id` — у `@userinfobot`.

### 1. Проверить, что логика работает

```bash
python selftest.py
```

### 2. Набрать кандидатов

Возьми 5–10 минтов токенов, которые за последний месяц сделали x10+
(dexscreener → сортировка по росту), и найди тех, кто входил рано:

```bash
python discover.py --mint MINT1 --mint MINT2 --mint MINT3 --out candidates.txt
```

`--min-hits 2` значит «попал рано минимум в 2 разных токена» — один хит это лотерея.

### 3. Отфильтровать

```bash
python wallet_analyzer.py --wallets candidates.txt --out qualified.json
```

Из 200 кандидатов обычно проходят 0–5. Если прошло 0 — это нормальный результат,
а не поломка: добавь токенов в шаг 2 или ослабь пороги (осознанно, не «чтобы
хоть кто-то прошёл»).

### 4. Запустить радар

```bash
python radar_bot.py --wallets qualified.json
```

Команды в чате: `/stats` (замеренный winrate), `/open`, `/wallets`.

## Чего этот код не делает и не может

- **Не предсказывает рост.** Сигнал приходит после того, как умные деньги
  зашли, — это следование, а не предсказание. Опоздание 20–60 секунд неизбежно
  (`poll_interval_sec`). Хочешь быстрее — Helius **webhooks** вместо polling.
- **Не торгует.** Приватные ключи здесь не нужны и нигде не запрашиваются:
  анализ идёт только по публичному адресу. Никогда не вставляй seed-фразу
  в чужой код, включая этот.
- **Не спасёт от рага.** Проверки отсекают дешёвые схемы, но LP можно снять и
  через час после всех проверок.
- **Не даёт гарантий.** На мемкоинах нормально потерять весь депозит.
  Размер позиции считается от `risk_per_trade_pct` — 1% на сделку.
  Это не инвестиционная рекомендация; я не финансовый советник.

## Что стоит доделать под себя

- Helius webhooks вместо polling — минус задержка.
- Trailing stop от `peak_price` (поле в БД уже есть).
- Пересчёт `qualified.json` раз в неделю: кошельки выгорают, вчерашний топ
  через месяц льёт.
- Проверка LP burn/lock (сейчас косвенно через rugcheck).
- Разделение исходов на «TP1 / TP2 / TP3» вместо бинарного win/loss.
