# Memecoin Wallet Radar

Анализ кошельков Solana по on-chain данным + телеграм-радар, который присылает
сигнал, когда несколько проверенных кошельков одновременно заходят в один токен.

---

## Сначала важное: про 80–85%

Ты просил, чтобы каждая сделка была в плюсе с вероятностью 80%. Такого не
существует ни у одного трейдера, фонда или бота — на мемкоинах тем более.
Кто это обещает, продаёт подписку, а не сигналы.

**Но 80% winrate тебе и не нужен.** Считай:

| Стратегия | Winrate | Стоп | Тейк | Мат. ожидание на сделку |
|---|---|---|---|---|
| «нужен 80%» | 80% | −25% | +40% | 0.8·40 − 0.2·25 = **+27%** |
| реалистичная | 40% | −25% | +100% | 0.4·100 − 0.6·25 = **+25%** |
| реалистичная | 35% | −20% | +150% | 0.35·150 − 0.65·20 = **+39%** |

Третья строка **лучше** первой, хотя проигрывает 2 сделки из 3. Прибыль делает
не частота попаданий, а асимметрия: маленький фиксированный убыток против
большой открытой прибыли. Поэтому в конфиге целься в `expectancy`, а не в winrate.

### Любой winrate можно выставить прямо сейчас — и он ничего не стоит

Для цены без предсказуемого сноса вероятность дойти до тейка `+a` раньше стопа
`−b` равна `b / (a + b)`. Winrate — это не свойство стратегии, а **ручка**,
которую крутит расстояние до тейка:

| Стоп | Тейк | Winrate | Мат. ожидание |
|---|---|---|---|
| −25% | +100% | 20% | 0 |
| −25% | +40% | 38% | 0 |
| −25% | +25% | 50% | 0 |
| −25% | **+6.25%** | **80%** | **0** |

Последняя строка — ровно то, что просят словами «хочу 80%». Достигается одной
правкой: `take_profit_ladder_pct: [6]`. Проверьте сами: `0.8 · 6.25 − 0.2 · 25 = 0`.

Ноль в последней колонке не совпадение и не свойство конкретных чисел — он
выводится из формулы и держится для **любой** пары стоп/тейк. А после комиссий и
проскальзывания (на мемкоинах 3–5% за круг) ноль превращается в стабильный минус.

Отсюда главное: **winrate не несёт информации о прибыльности.** 80% попаданий по
+6% и 20% попаданий по +100% — это одна и та же стратегия с нулевым ожиданием,
отличается только ощущение от неё.

Прибыль появляется в одном случае: если вход лучше случайного, то есть у цены
после сигнала есть снос вверх. Отбор кошельков и конфлюэнс — попытка этот снос
поймать. `/stats` — честный замер, поймали или нет.

И ещё: кошелёк с winrate 90% может быть убыточным. Запусти `python selftest.py` —
там четыре реальных паттерна, включая кошелёк с 80% плюсовых сделок и минусом
по деньгам. Анализатор такие отсекает.

### Почему на трекерах полно кошельков с «90% winrate»

1. **Спрятанные мешки.** Считают только закрытые сделки. Раги остаются висеть
   в кошельке и в статистику не попадают. Здесь считаются две цифры:
   `winrate` и `winrate (мешки=0)` — вторая честная.
2. **Фарм микро-суммами.** 300 сделок по 0.02 SOL с профитом +5%. Флаг `farm_like_size`.
3. **Снайпер-боты.** Держат позицию 20 секунд. Руками ты за ними не успеешь
   физически. Флаг `sniper_bot`.
4. **Survivorship bias.** Кошелёк угадал 3 токена и попал в топ трекера, а 200
   таких же слились и их никто не видит. Отсюда `min_closed_trades: 30`.

Поэтому в конфиге стоит `max_win_rate: 0.85` — кошельки **выше** 85% отклоняются
как подозрительные. Ровно та цифра, которую ты искал, работает как красный флаг.

## Как реализовано «не присылать, если winrate ниже 80%»

Заранее вероятность неизвестна, поэтому она **замеряется**:

1. Каждый сигнал пишется в `signals.db` вместе с условиями входа
   (сколько кошельков зашло, ликвидность, возраст токена) → «бакет».
2. Бот сам ведёт сделку до тейка или стопа и записывает исход.
3. `signal_journal.gate()` смотрит фактический winrate по этому бакету.
4. `gate_mode: hard` → пока замеренный winrate ниже `target_hit_rate`,
   сигналы из этого бакета **не приходят вообще**. Ровно как ты просил.
5. `gate_mode: shadow` → приходят с пометкой, чтобы ты видел, что теряешь.

Честное предупреждение: с `target_hit_rate: 0.80` и `gate_mode: hard` бот, скорее
всего, замолчит навсегда — потому что ни один бакет столько не даёт. Это не баг,
это и есть ответ на вопрос «бывает ли 80%». Начни с `0.45` и тейком `+100%`,
через месяц посмотри `/stats` и решай по реальным цифрам.

## Профили отбора

В начале `config.yaml` стоит один ключ:

```yaml
profile: balanced    # balanced | strict
```

| | `balanced` | `strict` |
|---|---|---|
| кошельков в конфлюэнсе | 2 | **3** |
| окно | 30 мин | **20 мин** |
| суммарный объём | 3 SOL | **8 SOL** |
| возраст токена | до 3 суток | **до суток** |
| ликвидность | от $15k | **от $50k** |
| FDV | до $5M | **до $2M** |
| топ-10 холдеров | до 35% | **до 25%** |
| сделок у кошелька | от 30 | **от 50** |
| profit factor кошелька | от 1.3 | **от 1.8** |

**Профиль отвечает только за отбор.** Реакция на низкий winrate настраивается
отдельно в `risk` — это независимое решение, и склеивать его с порогами отбора
было ошибкой:

```yaml
risk:
  target_hit_rate: 0.45     # цель, по которой судит гейт
  gate_mode: "shadow"       # shadow = присылать с пометкой, но замерять
                            # hard   = молчать, пока winrate ниже цели
```

Что даёт `strict` на самом деле: сигналов в разы меньше, качество входов выше,
winrate реалистично растёт с ~35% до ~45–50%. **До 80% отбор не доводит** —
восьмидесяти даёт только короткий тейк (см. таблицу выше), и он же обнуляет
прибыль.

Поэтому `gate_mode: hard` при цели 0.80 почти наверняка означает тишину. Связка
`strict` + `shadow` + `0.45` — рабочий компромисс: отбор жёсткий, сигналы
приходят с пометкой, и через месяц `/stats` покажет реальные цифры вместо
предположений.

Правки требуют перезапуска: `systemctl restart radar` на сервере.

## Файлы

| Файл | Что делает |
|---|---|
| `wallet_analyzer.py` | тянет свопы, восстанавливает сделки по FIFO, считает winrate / expectancy / profit factor, ставит красные флаги, отбирает годные кошельки |
| `discover.py` | ищет ранних покупателей уже отработавших токенов → список кандидатов |
| `token_safety.py` | ликвидность, FDV, mint/freeze authority, топ-10 холдеров, rugcheck |
| `signal_journal.py` | sqlite-журнал сигналов + замеренный winrate + гейт |
| `radar_bot.py` | телеграм-бот: конфлюэнс покупок → проверки → сигнал → ведение до TP/SL |
| `selftest.py` | проверка всей логики на синтетике, без API-ключей |
| `doctor.py` | проверяет токен, chat_id, ключ Helius и сеть — отвечает, почему бот молчит |
| `config.yaml` | все пороги |
| `.env.example` | шаблон для ключей |

## Установка

```bash
pip install -r requirements.txt
cp .env.example .env      # вписать ключи
```

`.env` читается автоматически при запуске любого скрипта — экспортировать
переменные вручную не нужно. Значение из окружения перебивает файл, так что
в systemd/docker ключи можно передавать как обычно.

Нужен один ключ: [helius.dev](https://helius.dev) (бесплатный тариф хватает для
старта). Dexscreener и rugcheck работают без ключа.

Токен бота — у `@BotFather`, `chat_id` — у `@userinfobot`.

Если переменная не задана, скрипт скажет об этом при запуске и не пойдёт
делать бессмысленные запросы. Команды бот принимает только из чата
`TELEGRAM_CHAT_ID` — имя бота публично, и посторонний не должен вычитывать
`/stats` и `/open`.

### 1. Проверить, что логика работает

```bash
python selftest.py
```

### 2. Набрать кандидатов

Возьми 5–10 минтов токенов, которые за последний месяц сделали x10+
(dexscreener → сортировка по росту), и найди тех, кто входил рано:

```bash
python discover.py --mint MINT1 --mint MINT2 --mint MINT3 --out candidates.txt
```

`--min-hits 2` значит «попал рано минимум в 2 разных токена» — один хит это лотерея.

Если в логе появится предупреждение «до первых покупок не долистали», у токена
слишком длинная история: ранние покупатели по нему найдены не будут, возьми
монету посвежее.

### 3. Отфильтровать

```bash
python wallet_analyzer.py --wallets candidates.txt --out qualified.json
```

Из 200 кандидатов обычно проходят 0–5. Если прошло 0 — это нормальный результат,
а не поломка: добавь токенов в шаг 2 или ослабь пороги (осознанно, не «чтобы
хоть кто-то прошёл»).

### 4. Запустить радар

```bash
python radar_bot.py --wallets qualified.json
```

Или одной командой — она сама поставит зависимости, прогонит диагностику и
поднимет радар: `sh run.sh` (Linux/macOS), двойной клик по `run.bat` (Windows).

> **Кнопка Start в Telegram ничего не запускает.** Она только отправляет боту
> сообщение `/start`. У бота нет своего сервера: читать команды и присылать
> сигналы должен процесс `radar_bot.py`, работающий на компьютере. Пока он не
> запущен, бот молчит — и это не поломка. Закроете терминал или уснёт ноутбук —
> радар остановится; для круглосуточной работы нужен VPS.

### Команды в чате

Список отдаётся в меню Telegram при старте, так что набирать вручную не нужно —
он появится по кнопке слева от поля ввода.

| Что происходит | |
|---|---|
| `/status` | жив ли радар, аптайм, сколько всего насчитал |
| `/open` | открытые сигналы с текущей ценой и просадкой от пика |
| `/watch` | токены, набирающие конфлюэнс, но ещё не ставшие сигналом |

| Результаты | |
|---|---|
| `/stats` | замеренный winrate по бакетам условий |
| `/history` | последние закрытые сигналы с исходом в R |

| Настройки | |
|---|---|
| `/wallets` | за какими кошельками слежу |
| `/settings` | текущие пороги входа, риска и безопасности |
| `/pause` · `/resume` | приглушить сигналы и вернуть их |

`/watch` стоит отдельного слова: он отвечает на вопрос «бот сломался или просто
молчит». Видно, что радар считает прямо сейчас и сколько не хватает до сигнала.

`/pause` глушит только доставку. Сигналы продолжают писаться в журнал, поэтому
замер winrate за время паузы не прерывается.

### Если бот молчит

```bash
python doctor.py
```

Радар намеренно не падает на сетевых ошибках — иначе его ронял бы любой
таймаут Helius. Обратная сторона: молчание в чате выглядит одинаково при
отозванном токене, чужом `chat_id`, второй запущенной копии и неоткрытом
диалоге. `doctor.py` проверяет каждый пункт отдельно и говорит, что чинить.

Самое частое: **бот не может написать первым.** Пока вы не открыли с ним чат
и не нажали Start, Telegram отвечает `chat not found` на каждое сообщение.

Отчёт всегда сохраняется в `doctor.log` — даже если окно закрылось.

### Если Telegram недоступен у провайдера

Симптом: `doctor.py` пишет «до api.telegram.org не достучались», а Helius при
этом отвечает. Значит интернет цел, закрыт именно Telegram API — у российских
провайдеров это обычное дело.

Пропишите прокси в `.env`, VPN тогда не нужен:

```
HTTPS_PROXY=http://логин:пароль@адрес:порт
```

Для socks5 дополнительно `pip install aiohttp-socks`. Пароль в логи не
попадает — он маскируется.

> **Системный прокси Windows на бота не влияет.** Его читают браузеры, а Python
> нет: включённый в «Параметры → Сеть и Интернет → Прокси-сервер» адрес радар
> проигнорирует. Работает либо `HTTPS_PROXY` в `.env`, либо режим TUN
> («Глобальный») в самом VPN-клиенте — он заворачивает весь трафик машины.
>
> Клиенты вроде v2rayN обычно поднимают локальный прокси на `127.0.0.1:10809`
> (HTTP) и `127.0.0.1:10808` (socks). Если такой клиент запущен, в `.env`
> достаточно строки `HTTPS_PROXY=http://127.0.0.1:10809`.
>
> Если браузер вдруг начал спрашивать логин и пароль «для доступа на
> прокси-сервер 127.0.0.1» — это клиент прописал себя системным прокси, а сам
> выключен. Лечится запуском клиента или выключением прокси в настройках
> Windows; вводить туда пароль не нужно.

Надёжнее всего — VPS за границей: радар всё равно должен работать
круглосуточно, а дома для этого пришлось бы не выключать компьютер.

## Запуск на VPS

Дома радар живёт, пока включён компьютер: закрыли крышку ноутбука — сигналы
прекратились. На сервере он работает сам, переживает перезагрузки и обрывы
сети. Плюс обходит блокировку Telegram, если сервер стоит за границей.

**1. Арендуйте VPS.** Хватит самого дешёвого: 1 ядро, 1 ГБ памяти. Образ —
**Ubuntu 24.04**. Локация — Европа: в российских дата-центрах будет ровно та же
блокировка, от которой вы уходите. После оплаты придёт IP-адрес и пароль root.

**2. Подключитесь.** В Windows откройте PowerShell и введите (IP — свой):

```powershell
ssh root@123.45.67.89
```

Первый раз спросит про отпечаток ключа — ответьте `yes`. Пароль при вводе не
отображается, это нормально.

**3. Поставьте радар:**

```bash
curl -fsSL https://raw.githubusercontent.com/gytfel/Memkoin-radar/claude/telegram-bot-launch-usbos3/deploy/setup.sh -o setup.sh
bash setup.sh
```

Скрипт ставит зависимости, кладёт код в `/opt/memkoin-radar`, заводит
пользователя без прав входа и регистрирует systemd-сервис. Бот пока не
запускается — сначала ключи.

**4. Впишите ключи:**

```bash
nano /opt/memkoin-radar/.env
```

Сохранить — `Ctrl+O`, `Enter`, выйти — `Ctrl+X`.

**5. Проверьте и запустите:**

```bash
cd /opt/memkoin-radar && sudo -u radar .venv/bin/python doctor.py
systemctl enable --now radar
```

`enable --now` означает «запустить сейчас и поднимать при каждой загрузке».

### Дальше пригодится

```bash
systemctl status radar      # работает ли
journalctl -u radar -f      # живой лог, выйти Ctrl+C
systemctl restart radar     # после правки .env
bash setup.sh               # обновить код, .env не тронется
```

Логи идут в journald, где ротация уже настроена, — файл `radar.log` на сервере
не нужен и рос бы бесконечно. Сервис перезапускается сам через 10 секунд после
любого падения.

Если и радар «ничего не выводит», запустите его с логом в файл:

```bash
python radar_bot.py --wallets wallets.txt --log-file radar.log
```

Туда попадает всё, включая причину, по которой запуск оборвался. Пустой
`radar.log` означает, что процесс не стартовал вообще, — тогда дело не в
конфиге, а в самой команде запуска.

## Чего этот код не делает и не может

- **Не предсказывает рост.** Сигнал приходит после того, как умные деньги
  зашли, — это следование, а не предсказание. Опоздание 20–60 секунд неизбежно
  (`poll_interval_sec`). Хочешь быстрее — Helius **webhooks** вместо polling.
- **Не торгует.** Приватные ключи здесь не нужны и нигде не запрашиваются:
  анализ идёт только по публичному адресу. Никогда не вставляй seed-фразу
  в чужой код, включая этот.
- **Не спасёт от рага.** Проверки отсекают дешёвые схемы, но LP можно снять и
  через час после всех проверок.
- **Не даёт гарантий.** На мемкоинах нормально потерять весь депозит.
  Размер позиции считается от `risk_per_trade_pct` — 1% на сделку.
  Это не инвестиционная рекомендация; я не финансовый советник.

## Что стоит доделать под себя

- Helius webhooks вместо polling — минус задержка.
- Trailing stop от `peak_price` (поле в БД уже есть).
- Пересчёт `qualified.json` раз в неделю: кошельки выгорают, вчерашний топ
  через месяц льёт.
- Проверка LP burn/lock (сейчас косвенно через rugcheck).
- Разделение исходов на «TP1 / TP2 / TP3» вместо бинарного win/loss.
